# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Sample web store built for learning AI-assisted coding:
- `backend/`: Spring Boot 4.2 on Java 27, SQL Server
- `frontend/`: Angular 22
- `cloud/`: a Spring Cloud sample (Eureka, Gateway, two microservices). The shop backend registers in Eureka as `eshop`, and the gateway can front it.

Angular-specific coding rules are in `frontend/CLAUDE.md` (generated by the Angular CLI). Follow them for any frontend change.

## Environment: always use the project-local toolchain

Every Bash command that runs java/mvn/node/npm/npx must start with `source ./dev-env.sh` (from the repo root). In PowerShell, use `. .\dev-env.ps1`.

The global tools on this machine are wrong for this project:
- Node 18 is too old.
- Maven isn't installed globally.
- The global `JAVA_HOME` points to a deleted JDK.

The script sets session-only `PATH`, `JAVA_HOME`, `PLAYWRIGHT_BROWSERS_PATH` and `JAVA_TOOL_OPTIONS`. Never install or switch tools globally (no nvm use, no global npm/Maven installs). Put new tools under `.tools/` or `maven/` instead.

Network gotchas:
- The network uses TLS inspection. Java needs `-Djavax.net.ssl.trustStoreType=Windows-ROOT`, which dev-env sets through `JAVA_TOOL_OPTIONS`. Without it, Maven fails with `PKIX path building failed`.
- The Bash sandbox blocks network access for mvn/npm/playwright. Commands that download dependencies need the sandbox disabled.

## Architecture

### Auth: one token type for everything

The API (`/api/**`) is stateless. It only accepts the app's own **HS256 JWT**, which `auth/JwtService` issues with these claims:
- `sub` = `users.id`
- `email`
- `role` = USER|ADMIN

How each kind of sign-in gets that token:
- **Local login:** `POST /api/auth/login` (or `register`) returns the JWT directly.
- **Google/Facebook:**
  1. A full-page redirect to `http://localhost:8080/oauth2/authorization/{id}`.
  2. Spring's `oauth2Login` handles the provider callback.
  3. `OAuth2LoginSuccessHandler` creates or updates the user and redirects to `:4200/auth/callback?code=…` with a single-use 60-second code from `OneTimeCodeStore`, which is in-memory.
  4. Angular exchanges the code via `POST /api/auth/exchange`.

  The JWT never appears in a URL.

`config/SecurityConfig` has two filter chains:
- `@Order(1)` for `/api/**`: JWT resource server, with CSRF off and sessions off.
- `@Order(2)` for everything else: OAuth2 login (needs a short session) and Swagger.

`oauth2Login` is only enabled when a `ClientRegistrationRepository` bean exists, which means Google/Facebook credentials are configured. Without them the app still runs, and `/api/auth/providers` returns `[]` so the UI hides the buttons.

Account rules:
- Admins are LOCAL accounts only. `AdminSeeder` creates the first one from `eshop.admin.*`.
- A social login whose email belongs to an account with a different provider is refused, not linked.

Admin endpoints are protected twice: by the URL rule `/api/admin/**` and by `@PreAuthorize` on `AdminController`.

In the frontend:
- The session lives in the NgRx store (`core/auth/`). See "NgRx" under the frontend layout.
- Selectors decode the role from the JWT payload, so the guards (`auth.guards.ts`) work synchronously. The guards only hide UI; the server is the authority.
- `auth.interceptor` adds the stored Bearer token, unless the request already has an `Authorization` header (as `AuthApi.me(token)` does during sign-in). It dispatches `sessionExpired` on a 401 from an authenticated call other than login/register/exchange.

### Backend layout (package by feature, `com.example.eshop`)

The packages are `auth`, `user`, `product`, `order`, `admin`, `config` and `common`.
- Controllers return DTO records, never entities.
- `open-in-view` is off. DTOs are mapped inside `@Transactional` service methods, because `OrderDto.from` touches lazy associations.
- Domain rules live in the entities:
  - `Order.addItem` decrements stock.
  - `Order.changeStatus` enforces `OrderStatus.canTransitionTo` and restores stock on CANCELLED.
- Order lines snapshot product name and price. Orders snapshot the shipping address.
- `OrderService.place` loads products with `PESSIMISTIC_WRITE`, so concurrent orders can't oversell.
- Errors become RFC 9457 ProblemDetail through `common/GlobalExceptionHandler`:
  - `NotFoundException` → 404
  - `BusinessException` → 409
  - `BadCredentialsException` → 401
  - validation errors → 400

  The frontend reads `detail` from these through `core/errors.ts`.
- Paged endpoints return `common/PageResponse`, not Spring's `Page`.

### Database

Flyway (`src/main/resources/db/migration`) owns the schema. Hibernate runs with `ddl-auto=validate`, so any entity change needs a new `V<n>__*.sql` migration.

SQL Server specifics:
- `Instant` maps to `DATETIMEOFFSET`.
- Strings are `NVARCHAR`, because `hibernate.use_nationalized_character_data=true`.
- The table is `orders`, because `order` is reserved.

Locally, the backend uses **Windows integrated auth**:
- The server is in Windows-auth-only mode.
- The JDBC native DLL is in `.tools/mssql-jdbc-auth`. Its version must match the `mssql-jdbc` version from the Spring Boot BOM; re-download it after a Boot upgrade.
- `mvn spring-boot:run` finds the DLL through `-Djava.library.path` in the spring-boot-maven-plugin `jvmArguments` (pom.xml). An IDE launch needs the same VM argument; otherwise it fails with `Unable to load authentication DLL`.

Integration tests use Testcontainers (`TestcontainersConfiguration`, `mcr.microsoft.com/mssql/server:2022-latest`). They never touch the local DB.

### Spring Cloud sample (`cloud/`)

`cloud/pom.xml` is both the aggregator and the parent:
- Its parent is Boot 4.2.0, and it imports the Spring Cloud **2026.0.0** BOM. That is the release train for Boot 4.2; check `start.spring.io/actuator/info` → `bom-ranges` before upgrading either.
- Its modules are `discovery-server` (Eureka, :8761), `gateway` (:8090), `arithmetic-service` (:8081) and `string-service` (:8082).

The gateway:
- Uses `spring-cloud-starter-gateway-server-webmvc`, the servlet flavour.
- Declares its routes in YAML under `spring.cloud.gateway.server.webmvc.routes`, with `lb://<spring.application.name>` URIs resolved through Eureka.
- Passes paths through unchanged, so each service already serves its own `/api/<area>/**` prefix.

Services:
- Set `eureka.instance.instance-id=${spring.application.name}:${server.port}` and return it as `servedBy`, which makes load balancing visible.
- Use short lease and fetch intervals, and the registry has self-preservation off. These are dev settings.
- The port is `${PORT:<default>}`, so you can start extra instances on other ports.
- Turn invalid input into a 400 ProblemDetail: `IllegalArgumentException` through their `ErrorHandler`, and parameter errors through `spring.mvc.problemdetails.enabled`.

The shop backend in the gateway:
- `backend/` imports the same Spring Cloud BOM and uses the Eureka client.
  - It registers as `eshop:8080` and logs warnings when Eureka is down.
  - `EUREKA_ENABLED=false` turns this off, and `EshopFlowIT` sets `eureka.client.enabled=false`.
- The gateway's `eshop` route matches `/api/**`, `/oauth2/**`, `/login/oauth2/**` and Swagger, and must stay **last** in the route list, or it would capture `/api/arithmetic/**` and `/api/strings/**`.
- The route uses `PreserveHostHeader`, so the OAuth2 redirect URIs that Spring builds point to `:8090`.
- On the frontend, `npm run start:gateway` (the `gateway` configuration in `angular.json`) proxies `/api` to `:8090` and swaps `core/config.ts` for `config.gateway.ts` (`BACKEND_ORIGIN`).

`GatewayRoutingTest`:
- Disables Eureka and uses Spring Cloud's *simple* discovery client (`spring.cloud.discovery.client.simple.instances.*`) pointing at JDK `HttpServer` stubs.
- To add a route, add it to `gateway/application.yml` and add a stub and test there.

### Frontend layout (`frontend/src/app`)

- `core/`: services (`@Service()` decorator, Angular 22), interceptor, guards, models that mirror the backend DTOs, and `NEXT_STATUSES`, which mirrors `OrderStatus.canTransitionTo`.
- `features/shop`: customer area under `ShopLayout`.
- `features/admin`: lazy `ADMIN_ROUTES` under `AdminLayout`, behind `adminGuard`.
- `features/auth`: login, register and the OAuth callback. The login page hides social buttons when `returnUrl` starts with `/admin`.
- `features/shared`: profile page (used in both areas), field-error, status chip.

Patterns used throughout:
- Reads use `httpResource` in components; writes go through `ShopApi` / `AdminApi` (Observables).
- Forms use **Signal Forms**: `form(model, schema, { submission: { action } })` with `<form [formRoot]>` and `[formField]`.
- Text inputs must bind to `string` fields, not `string | null`.
- Route params and query params arrive as `input()`s via `withComponentInputBinding()`.
- **NgRx Store** (classic: actions, reducers, selectors, effects) holds the session and the cart:
  - Each slice lives in its own folder:
    - `core/auth/`: `AuthActions`, `authFeature`, selectors, `AuthEffects`, and `AuthApi` for the stateless HTTP calls.
    - `core/cart/`: `CartActions`, `cartFeature`, selectors, `CartEffects`.
  - Both are registered in `app.config.ts`.
  - Components read with `store.selectSignal(selectX)` and write with `store.dispatch(XActions.y(...))`.
  - Reducers and selectors stay pure: no `Date.now()`, no storage. Effects do HTTP, storage and navigation:
    - Auth: on `ROOT_EFFECTS_INIT`, restore the token from sessionStorage (expired tokens are dropped), then `loadUser`.
    - Auth: after `signInSucceeded`, navigate to `returnUrl`, or to `/admin` for admins and `/` for everyone else.
    - Auth: a `timer` fires `sessionExpired` at the JWT's `exp`. It runs inside `switchMap`, so a new session or a logout cancels it.
    - Auth: login, register and exchange use `exhaustMap`, so double submits are ignored.
    - Cart: restore from and save to localStorage.
  - The auth pages only dispatch actions and render `selectAuthPending` and `selectAuthError`. They dispatch `clearError` when opened.
  - Profile and checkout form models are `linkedSignal`s over the stored user.
  - `maskSecrets` keeps passwords out of the Redux DevTools action log.
  - Page data still uses `httpResource`. Move state to NgRx only on purpose.
- The cart is client-side only. The server re-validates stock when the order is placed.

Testing notes:
- In unit tests, don't `await fixture.whenStable()` while an `httpResource` request is still unflushed; it waits forever. Use `TestBed.tick()`, flush, then `whenStable()`.
- NgRx tests:
  - Reducers and selectors are plain function calls; no TestBed needed.
  - Effects use `provideMockActions` with fake `AuthApi`/`Router` values. Timers use `vi.useFakeTimers()`.
  - Components, guards and the interceptor use `provideMockStore({ initialState: { auth: {...initialAuthState, token} } })` and spy on `store.dispatch`.
- E2E tests create a fresh customer per test and assume the seeded admin (`admin@eshop.local` / `Admin123!`, overridable with `E2E_ADMIN_*`).
