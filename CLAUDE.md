# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Sample web store built for learning AI-assisted coding:
- `backend/`: Spring Boot 4.2 on Java 27, SQL Server
- `frontend/`: Angular 22
- `cloud/`: Spring Cloud (Eureka, Gateway), the OAuth2/OIDC **auth-server** that issues every token, two small microservices, and a Spring AI **ai-service**. The shop backend registers in Eureka as `eshop`, and the gateway can front it.

Angular-specific coding rules are in `frontend/CLAUDE.md` (generated by the Angular CLI). Follow them for any frontend change.

## Environment: always use the project-local toolchain

Every Bash command that runs java/mvn/node/npm/npx must start with `source ./dev-env.sh` (from the repo root). In PowerShell, use `. .\dev-env.ps1`.

The global tools on this machine are wrong for this project:
- Node 18 is too old.
- Maven isn't installed globally.
- The global `JAVA_HOME` points to a deleted JDK.

The script sets session-only `PATH`, `JAVA_HOME`, `PLAYWRIGHT_BROWSERS_PATH` and `JAVA_TOOL_OPTIONS`. Never install or switch tools globally (no nvm use, no global npm/Maven installs). Put new tools under `.tools/` or `maven/` instead.

Network gotchas:
- The network uses TLS inspection. Java needs `-Djavax.net.ssl.trustStoreType=Windows-ROOT`, which dev-env sets through `JAVA_TOOL_OPTIONS`. Without it, Maven fails with `PKIX path building failed`.
- The Bash sandbox blocks network access for mvn/npm/playwright. Commands that download dependencies need the sandbox disabled.

## Architecture

### Auth: OAuth2 / OpenID Connect with `cloud/auth-server`

`cloud/auth-server` (:9000) is a **Spring Authorization Server**. It is part of Spring Security 7 and uses the starter `spring-boot-starter-security-oauth2-authorization-server`.
- **Accounts** live in its own database `eshop_identity`. Its `accounts` table holds the password hash, role and provider.
- **Pages:** it hosts the Thymeleaf sign-in and registration pages.
- **Google/Facebook** are federated here. The auth server is an `oauth2Login` client of them, and `SocialLoginHandler` creates the account.
- **Admin:** `AdminSeeder` creates the first admin from `identity.admin.*`, set in the gitignored `application-local.yml`, which `spring.config.import` loads automatically.
- **Clients** are registered in YAML under `spring.security.oauth2.authorizationserver.client`:
  - `eshop-web`: public client, Authorization Code with PKCE required.
  - `dev-cli`: client credentials, for curl.
- **Signing key:** Boot generates the RSA key and `JWKSource` at startup, so a restart invalidates every token.
- **Session cookie** is named `AUTHSESSION`, because all `localhost` ports share cookies.

The auth server has two filter chains:
- Its protocol endpoints use `http.oauth2AuthorizationServer(...)` with OIDC enabled.
- The login chain covers form login and the optional `oauth2Login`.

`AccountClaims` (an `OAuth2TokenCustomizer`) puts these claims into access and ID tokens:
- `sub` = account id
- `email`
- `role` = USER|ADMIN
- `provider`
- `given_name` / `family_name`

Gotchas:
- `RegisterController` signs the new user in by hand. Spring Security 7 then needs a `FactorGrantedAuthority` (`PASSWORD_AUTHORITY`, with `issuedAt`) among the authorities, or the ID token fails with "authenticationTime cannot be null".
- In MockMvc, GET parameters for `/oauth2/authorize` must use `.queryParam()`, not `.param()`. The endpoint reads the real query string.

Account rules:
- Admins are LOCAL accounts only.
- A social sign-in whose email belongs to an account with another provider is refused, not linked.

**Resource servers:** `backend`, arithmetic-service, string-service and ai-service.
- Each sets only `spring.security.oauth2.resourceserver.jwt.issuer-uri` (`AUTH_ISSUER`, default `http://localhost:9000`). Keys come from the JWKS, fetched lazily on the first request.
- A converter maps the `role` claim to `ROLE_*`.
- The backend's admin endpoints are protected twice: by the URL rule `/api/admin/**` and by `@PreAuthorize` on `AdminController`.
- In tests, inject tokens with spring-security-test's `jwt()` and set authorities explicitly; the auth server isn't needed.

**Backend users** (`user/`):
- `users.subject` (Flyway V3) links a shop user to the token's `sub`.
- `CurrentUsers.get(jwt)` resolves the user:
  - It finds the user by subject and syncs email, role and provider from the token.
  - Otherwise it provisions one (`UserProvisioner`, in `REQUIRES_NEW` transactions). An existing row with the same email is taken over; otherwise a new row is created with its profile names taken from the token.
- Tokens without an `email` (machine tokens) get a 403.
- `GET /api/auth/me` is all that is left of the old auth API. The app calls it right after sign-in.

**In the frontend** (`core/auth/`, NgRx):
- `login` → `AuthEffects.login$`:
  1. Creates the PKCE verifier, challenge and state (`pkce.ts`, Web Crypto).
  2. Stores verifier, state and `returnUrl` in sessionStorage (`eshop.pendingSignIn`).
  3. Redirects to `/oauth2/authorize`.
- `/auth/callback?code&state` → `exchangeCode` → `exchangeCode$`:
  1. Checks the state.
  2. Posts code plus verifier as a form to `/oauth2/token`.
  3. Loads `/api/auth/me` with the new token.
  4. Dispatches `signInSucceeded({ token, idToken, user, returnUrl })`.
- `logout` → `logout$` reads the ID token, clears storage, then redirects to `/connect/logout?id_token_hint=…&post_logout_redirect_uri=…`. It dispatches `loggedOut`; the reducer keeps the state on `logout` so the effect can still read the ID token.
- The `/login` route only dispatches `login`. `/register` redirects to it; registration is a page of the auth server.
- Selectors decode the role from the access token, so the guards work synchronously. The guards only hide UI; the servers are the authority.
- `auth.interceptor` adds the stored Bearer token to `/api/` calls only, unless the request already has an `Authorization` header. It dispatches `sessionExpired` on a 401.
- `maskSecrets` / `maskTokensInState` keep tokens and codes out of Redux DevTools.

### Backend layout (package by feature, `com.example.eshop`)

The packages are `auth`, `user`, `product`, `order`, `admin`, `config` and `common`.
- Controllers return DTO records, never entities.
- `open-in-view` is off. DTOs are mapped inside `@Transactional` service methods, because `OrderDto.from` touches lazy associations.
- Domain rules live in the entities:
  - `Order.addItem` decrements stock.
  - `Order.changeStatus` enforces `OrderStatus.canTransitionTo` and restores stock on CANCELLED.
- Order lines snapshot product name and price. Orders snapshot the shipping address.
- `OrderService.place` loads products with `PESSIMISTIC_WRITE`, so concurrent orders can't oversell.
- Errors become RFC 9457 ProblemDetail through `common/GlobalExceptionHandler`:
  - `NotFoundException` → 404
  - `BusinessException` → 409
  - `BadCredentialsException` → 401
  - validation errors → 400

  The frontend reads `detail` from these through `core/errors.ts`.
- Paged endpoints return `common/PageResponse`, not Spring's `Page`.

### Database

Flyway (`src/main/resources/db/migration`) owns the schema. Hibernate runs with `ddl-auto=validate`, so any entity change needs a new `V<n>__*.sql` migration.

SQL Server specifics:
- `Instant` maps to `DATETIMEOFFSET`.
- Strings are `NVARCHAR`, because `hibernate.use_nationalized_character_data=true`.
- The table is `orders`, because `order` is reserved.

Locally, the backend uses **Windows integrated auth**:
- The server is in Windows-auth-only mode.
- The JDBC native DLL is in `.tools/mssql-jdbc-auth`. Its version must match the `mssql-jdbc` version from the Spring Boot BOM; re-download it after a Boot upgrade.
- `mvn spring-boot:run` finds the DLL through `-Djava.library.path` in the spring-boot-maven-plugin `jvmArguments` (pom.xml). An IDE launch needs the same VM argument; otherwise it fails with `Unable to load authentication DLL`.

Integration tests use Testcontainers (`TestcontainersConfiguration`, `mcr.microsoft.com/mssql/server:2022-latest`). They never touch the local DB.

### Spring Cloud sample (`cloud/`)

`cloud/pom.xml` is both the aggregator and the parent:
- Its parent is Boot 4.2.0, and it imports the Spring Cloud **2026.0.0** BOM. That is the release train for Boot 4.2; check `start.spring.io/actuator/info` → `bom-ranges` before upgrading either.
- Its modules are `discovery-server` (Eureka, :8761), `gateway` (:8090), `arithmetic-service` (:8081), `string-service` (:8082), `auth-server` (:9000, see Auth) and `ai-service` (:8084).
- It also imports the **Spring AI 2.1.0** BOM, the release for Boot 4.2.

`ai-service` (Spring AI):
- `DescriptionWriter` builds its own `ChatClient` from `ObjectProvider<ChatModel>`, with `spring.ai.chat.client.enabled=false`. With no model configured it throws `AiUnavailableException`, which becomes a 503 with instructions. Provider errors become a 502.
- `spring.ai.model.chat` = `AI_PROVIDER` (`anthropic` | `ollama` | `none`, default `none`).
- `spring.ai.model.embedding` and `spring.ai.model.decision` are `none`. Spring AI 2.1's Ollama decision model would otherwise connect to Ollama at startup, even when the provider is Anthropic.
- Anthropic: model `claude-opus-5-5` (overridable with `ANTHROPIC_MODEL`). Don't set `temperature`, because current Claude models reject it.
- Structured output: `.call().entity(DescriptionSuggestion.class)`.
- `/api/ai/**` is ADMIN-only.
- Tests use a fake `ChatModel`, and `AiProviderSelectionTest` starts the whole app with each provider setting.

The gateway:
- Uses `spring-cloud-starter-gateway-server-webmvc`, the servlet flavour.
- Declares its routes in YAML under `spring.cloud.gateway.server.webmvc.routes`, with `lb://<spring.application.name>` URIs resolved through Eureka.
- Passes paths through unchanged, so each service already serves its own `/api/<area>/**` prefix.

Services:
- Set `eureka.instance.instance-id=${spring.application.name}:${server.port}` and return it as `servedBy`, which makes load balancing visible.
- Use short lease and fetch intervals, and the registry has self-preservation off. These are dev settings.
- The port is `${PORT:<default>}`, so you can start extra instances on other ports.
- Turn invalid input into a 400 ProblemDetail: `IllegalArgumentException` through their `ErrorHandler`, and parameter errors through `spring.mvc.problemdetails.enabled`.

The shop backend in the gateway:
- `backend/` imports the same Spring Cloud BOM and uses the Eureka client.
  - It registers as `eshop:8080` and logs warnings when Eureka is down.
  - `EUREKA_ENABLED=false` turns this off, and `EshopFlowIT` sets `eureka.client.enabled=false`.
- The gateway's `eshop` route matches `/api/**` and Swagger. It must stay **last** in the route list, or it would capture the `arithmetic`, `strings` and `ai` routes. It uses `PreserveHostHeader`.
- The gateway passes `Authorization` through and doesn't validate tokens itself; each service does.
- The auth server is **not** routed. The issuer needs one stable URL, and the browser goes to `:9000` directly.
- On the frontend, `npm run start:gateway` (the `gateway` serve configuration) proxies `/api` to `:8090`. `npm start` uses `proxy.conf.json`, which sends `/api/ai` → `:8084` and `/api` → `:8080`.

`GatewayRoutingTest`:
- Disables Eureka and uses Spring Cloud's *simple* discovery client (`spring.cloud.discovery.client.simple.instances.*`) pointing at JDK `HttpServer` stubs.
- To add a route, add it to `gateway/application.yml` and add a stub and test there.

### Frontend layout (`frontend/src/app`)

- `core/`: services (`@Service()` decorator, Angular 22), interceptor, guards, models that mirror the backend DTOs, and `NEXT_STATUSES`, which mirrors `OrderStatus.canTransitionTo`.
- `features/shop`: customer area under `ShopLayout`.
- `features/admin`: lazy `ADMIN_ROUTES` under `AdminLayout`, behind `adminGuard`. `description-writer/` is the AI description dialog (MatDialog), opened from `AdminProducts`.
- `features/auth`: `login` (starts the redirect to the auth server) and `oauth-callback` (code + state → `exchangeCode`).
- `features/shared`: profile page (used in both areas), field-error, status chip.

Patterns used throughout:
- Reads use `httpResource` in components; writes go through `ShopApi` / `AdminApi` (Observables).
- Forms use **Signal Forms**: `form(model, schema, { submission: { action } })` with `<form [formRoot]>` and `[formField]`.
- Text inputs must bind to `string` fields, not `string | null`.
- Route params and query params arrive as `input()`s via `withComponentInputBinding()`.
- **NgRx Store** (classic: actions, reducers, selectors, effects) holds the session and the cart:
  - Each slice lives in its own folder:
    - `core/auth/`: `AuthActions`, `authFeature`, selectors, `AuthEffects`, and `AuthApi` for the stateless HTTP calls.
    - `core/cart/`: `CartActions`, `cartFeature`, selectors, `CartEffects`.
- Each component has its own folder holding `name.ts`, `name.html`, `name.scss` and `name.spec.ts`, e.g. `features/shop/cart/`. Route files (`admin.routes.ts`) and styles shared by several components (`features/auth/auth.scss`) sit one level up, in the area folder.
  - Both are registered in `app.config.ts`.
  - Components read with `store.selectSignal(selectX)` and write with `store.dispatch(XActions.y(...))`.
  - Reducers and selectors stay pure: no `Date.now()`, no storage. Effects do HTTP, storage and navigation:
    - Auth: the PKCE flow (see Auth above).
    - Auth: on `ROOT_EFFECTS_INIT`, restore the tokens from sessionStorage (`eshop.session`; expired ones are dropped), then `loadUser`.
    - Auth: after `signInSucceeded`, navigate to `returnUrl`, or to `/admin` for admins and `/` for everyone else.
    - Auth: a `timer` fires `sessionExpired` at the access token's `exp`. It runs inside `switchMap`, so a new session or a logout cancels it. Session expiry goes back through `/login` → auth server, which signs the user in again silently while its own session lives.
    - Cart: restore from and save to localStorage.
  - Profile and checkout form models are `linkedSignal`s over the stored user.
  - Page data still uses `httpResource`. Move state to NgRx only on purpose.
- The cart is client-side only. The server re-validates stock when the order is placed.

Testing notes:
- In unit tests, don't `await fixture.whenStable()` while an `httpResource` request is still unflushed; it waits forever. Use `TestBed.tick()`, flush, then `whenStable()`.
- NgRx tests:
  - Reducers and selectors are plain function calls; no TestBed needed.
  - Effects use `provideMockActions` with fake `AuthApi`/`Router` values; `AuthApi.redirect` wraps the full-page navigation, so it can be faked. Timers use `vi.useFakeTimers()`.
  - Components, guards and the interceptor use `provideMockStore({ initialState: { auth: {...initialAuthState, token} } })` and spy on `store.dispatch`.
- E2E tests sign in and register on the auth server's pages (`signIn` and `registerCustomer` in `e2e/helpers.ts`). They create a fresh customer per test and assume the admin seeded by the auth server (`admin@eshop.local` / `Admin123!`, overridable with `E2E_ADMIN_*`).
